# Zynq-7020 PYNQ 光路交互工程技能包提炼过程

## 一、提炼对象与工程基础

技能包以 Zynq-7020 实物光路交互系统为工程基础，将图像采集、物体检测、稳定姿态提交、光路计算、HDMI 显示和电脑网页交互中的实现方法，整理为相互衔接的七项技能。提炼过程围绕实际代码入口、接口约定、运行记录和构建产物展开，形成“工程材料整理—处理过程归纳—接口契约抽取—脚本与样例固化—分层验证”的组织方式。

工程采用 PYNQ 板端与电脑端协同运行结构。板端 Python 统一管理 Overlay、MMIO、GPIO、相机和帧缓冲；C 核心承担检测、B 防抖、Portal 规则、光路求解、协议处理与显示保持；电脑后台维护串口控制、时钟映射和游戏会话，网页呈现物体模型、光路、计时及结算。命令行与 Notebook 共用 Session，采集和显示由同一硬件所有者管理。

交互画面为 1280×720，摄像头输入采用双 lane、RAW10/BGGR，处理图像为 BGR888。实物包括 Mirror、Portal A、Portal B、Target 和 WALL，光源位置与初始方向取自关卡配置。这些具体条件构成技能提炼的工程实例，布局、所有权、时钟、接口和制品关系则被整理为可独立使用的方法。

材料入口：[工程总说明](../README.md)、[工程协作记录](大模型协作记录.md)、[优化过程](优化过程.md)、[复现说明](复现说明.md)、[技能包说明](../skill/README.md)。

## 二、工程材料的整理与规则抽取

### 1. 按运行链路组织材料

首先沿一帧数据的处理顺序梳理材料，将原始输入、处理函数、输出结果和验证记录放入同一条链路：

```text
相机与 PL 视频输入
        ↓
采集槽完成确认与 CPU 图像取得
        ↓
C 检测、稳定器与场景提交
        ↓
光路求解、画布合成及串口姿态输出
        ↓
HDMI 显示退休 / 电脑游戏会话与网页呈现
        ↓
停止请求、DMA 停机确认与缓冲释放
```

硬件构建材料另按“源码与配置—综合实现—布线检查点—报告—BIT/HWH/XSA”组织，与运行链路通过硬件接口、配置和文件摘要衔接。

## 三、七项技能的具体提炼过程

### 1. PYNQ 开发编排：从系统分工到会话与原生接口

**工程实践。** version14 板端以 Python 3.6 管理设备与调度，已有 C 检测、稳定器、Portal、协议和画面保持逻辑继续通过原生库使用。`beam_hardware.py` 提供硬件所有者，`beam_runtime.py` 封装帧数据和 C 调用，命令行与 Notebook 通过同一 Session 进入运行链路。

**提炼过程。** 先从运行说明提取板卡、PYNQ、Python、处理器和系统库条件，再沿 Python/C 交界整理帧尺寸、行步幅、结构体字段、函数签名、错误传播和所有权。C 库的目标条件统一为 Cortex-A9、ARMv7 hard-float 与目标 GLIBC 版本需求，构建记录与运行接口共同构成验收依据。

**形成的方法。** `pynq-development` 将开发任务组织为环境确认、BIT/HWH 文件解析、Overlay/IP 接入、Python/C 数组包装和 DMA 交接。数组接口显式记录 dtype、shape、stride、可写属性和输入输出关系；HWH 解析器输出模块、VLNV、参数及地址窗口。板端 Python 版本与主机工具版本分别记录，工程编排和离线工具使用各自对应的环境。

**落地文件。** [技能入口](../skill/pynq-development/SKILL.md)、[PYNQ 开发流程](../skill/pynq-development/references/pynq-workflow.md)、[C 库与 ctypes 模板](../skill/pynq-development/references/native-demo.md)、[HWH 解析器](../skill/pynq-development/scripts/inspect_hwh.py)。

**工程对应。** [硬件所有者](../src/project/pynq_vision/beam_hardware.py)、[运行接口](../src/project/pynq_vision/beam_runtime.py)、[C 构建入口](../build/build_c.py)、[复现说明](复现说明.md)。

### 2. DMA 契约：从帧槽交接到布局、同步与释放条件

**工程实践。** 单行图像有效数据为 `1280×3=3840` 字节，DMA 行步长为 5760 字节。单槽按 `5760×720=4,147,200` 字节分配；三槽采集与三槽显示各占 12,441,600 字节，合计 24,883,200 字节。CPU 取得图像时逐行复制有效数据，显示提交整幅画布，待退休槽保持设备所有权。

**提炼过程。** 以单个槽为对象，将分配、设备写入、完成确认、CPU 访问、设备读取、退休和释放逐项展开，再把数值布局与状态交接分别抽取。缓存同步描述数据可见性；完成和退休描述设备访问阶段；停止确认描述资源释放条件。三类信息在契约中分别记录。

生命周期示例进一步固定了提交顺序：在调用设备启动前移交所有权，启动过程出现异常时继续保留设备状态；退出使用单调期限、停止请求和结构化状态读取，在约定的停机状态满足后释放。源行步幅与目标行步幅分别传入，复制过程保持目标行填充。

**形成的方法。** `pynq-dma-contract` 用布局描述检查行字节、整行跨度、地址范围、对齐、槽间重叠和访问冲突，用生命周期示例表达提交、同步、停止与释放。布局算术和应用状态可在主机独立执行，真实设备状态由工程运行所有者记录。

**落地文件。** [技能入口](../skill/pynq-dma-contract/skill.md)、[布局格式](../skill/pynq-dma-contract/references/layout-schema.md)、[契约模板](../skill/pynq-dma-contract/references/contract-template.md)、[布局检查器](../skill/pynq-dma-contract/scripts/check_layout.py)、[生命周期示例](../skill/pynq-dma-contract/examples/lifecycle.py)。

**验证对应。** [18 项 DMA 主机检查日志](../sim/results/host_verified/dma_skill.log)包含 7 项布局检查和 11 项生命周期检查，覆盖步幅、跨度、地址、行填充、所有权、启动异常、状态读取和有界停机。设备运行的退出结果见[板端会话记录](../board/evidence/level1_run_1/board_session.txt)。

### 3. 光路交互集成：从物体姿态到完整场景提交

**工程实践。** 检测器输出五类实物的中心、方向和有效边界，稳定器确认姿态后交给场景与光路核心。光源由关卡配置定义，Mirror 使用有限反射面，Portal 的入口、出口与有向轴关联，Target 按目标边界判定命中。板端和电脑端共同使用已有的几何规则及配置来源。

Portal B 的出射策略由 `portal_b_exit_side=1` 表达：沿 solid→ring 有向轴的正法向 `(-axis.y, axis.x)`，从同侧长边垂直向外出射。旋转物块时，出口位置和方向随同一有向模型更新。

**提炼过程。** 沿“观测—稳定—提交—求解—呈现”分解调用关系，为每个阶段保留 generation、sequence、captured time、level 和质量字段。姿态稳定支持间隔、场景准入、校时质量与显示保持分别归类；模型和完整光段归入同一场景快照。

**形成的方法。** `ray-game-integration` 将坐标、身份、有限边界、稳定输出和权威会话作为集成主线。显示保留携带原始时间与帧号，新完整场景到达时整体替换；计分输入按场景准入与当前关卡身份判定。网页特效读取有效光段和事件，游戏结果由已有 C 会话计算。

**落地文件。** [技能入口](../skill/ray-game-integration/SKILL.md)、[共享配置](../src/project/pc_vision/game_config.json)、[稳定器](../src/project/color_test/software/vision_ps_baremetal/src/vision_stabilizer.c)、[游戏会话](../src/project/color_test/software/vision_ps_baremetal/src/game_session.c)、[光路核心](../src/project/color_test/software/vision_ps_baremetal/src/ray_game.c)。

**验证对应。** 第一关原始串口解析得到 66 帧姿态，保留选关、开始、姿态与重置身份；同一输入在两份 C 程序中形成的 69 份离线状态全部一致。现场记录为 3 星、20 秒多一点，离线 C 复核结果为 3 星、20181 ms，两类结果分别归档于[第一关记录](../board/evidence/level1_run_1/README.md)和[离线状态](../board/evidence/level1_run_1/offline_c_replay.jsonl)。

### 4. 流式性能分析：从阶段日志到同域窗口计算

**工程实践。** 优化报告分别统计采集与复制、C 处理与画布合成、显示阶段、串口传输和姿态提交。调度采用采集等待与显示退休轮询交叠的方式，日志中同时存在独立耗时、包含其他阶段的耗时和可重叠跨度。

**提炼过程。** 先定义指标的起止点和时钟来源，再按连接、启动区间与报告序号形成连续窗口。阶段类型分为 leaf、envelope、span、event 和 meta，分别表示独立阶段、包含阶段、跨度、计数事件和元信息。累计报告用相邻快照的差分还原样本数和总耗时。

窗口均值采用：

```text
新增样本数 = 后一报告累计样本数 - 前一报告累计样本数
新增耗时   = 后一报告累计耗时   - 前一报告累计耗时
窗口均值ms = 新增耗时us ÷ 新增样本数 ÷ 1000
```

**形成的方法。** `stream-perf-analysis` 固定输入字段、单位和窗口连续条件，按各阶段的包含与重叠关系解释结果。累计最大值保留累计含义，分位数按样本量及定义计算。工程事件型 UART 日志由已有串口解析器还原帧与控制身份，累计阶段日志由专用分析器处理。

**落地文件。** [技能入口](../skill/stream-perf-analysis/SKILL.md)、[日志格式](../skill/stream-perf-analysis/references/log-formats.md)、[分析器](../skill/stream-perf-analysis/scripts/analyze.py)、[累计报告样例](../skill/stream-perf-analysis/examples/performance.jsonl)、[阶段契约](../skill/stream-perf-analysis/references/project-perf-contract.json)。

**验证对应。** 包内累计样例有 62 行，对应两组报告；分析器得到报告 24→25 的一个有效窗口，包含 25 个非 meta 阶段和 6 个 meta 阶段。工程实际运行的阶段计时见[十帧记录](../board/evidence/user_stdout_test10_1cd08d5e.json)与[持续运行说明](../board/evidence/level1_run_1/README.md)。

### 5. FPGA 分层验证：从视频事件到报告判据

**工程实践。** 视频链路贯穿 CSI、RAW10/BGGR、像素转换、AXI 视频流、DDR 与 HDMI。工程验证同时保留协议事件、行数、像素顺序、时序条件和构建来源，针对不同对象使用相应检查层级。

**提炼过程。** 将验证对象拆分为接口协议、像素语义、时钟与复位、实现约束及文件身份。AXI 流按握手接受的 SOF、EOL、TLAST 和 TKEEP 统计；Bayer 路径按 RAW 位打包、BGGR 相位、裁剪奇偶和 DDR 字节顺序核对；实现阶段读取同次综合、布局布线、时序、CDC、DRC 和资源报告。

**形成的方法。** `fpga-verification-gates` 建立“对象—输入—判据—实际结果—证据文件”的记录结构。静态检查、主机模型、RTL 仿真、OOC、顶层实现和设备运行分别记录，各层结论与其实际输入和输出对应。

**落地文件。** [技能入口](../skill/fpga-verification-gates/SKILL.md)、[验收模板](../skill/fpga-verification-gates/references/acceptance-template.md)、[PL 构建流程](../build/pl_flow.md)。

**工程对应。** 在工程声明的 25%～75% UI 引脚过渡时序包络下，同次布线报告的 WNS 为 0.135 ns、WHS 为 0.052 ns、WPWS 为 0.264 ns，建立、保持和脉宽的失败端点数均为 0；资源为 7485 LUT、10738 寄存器、15 BRAM、0 DSP。上述数值对应[实现时序报告](../build/reports/sampling_window_build/reports/post_impl_timing.rpt)、[资源报告](../build/reports/sampling_window_build/reports/post_impl_utilization.rpt)与[制品绑定记录中的时序模型](../build/overlay_candidate/binding.json)。

### 6. 工具链与制品交接：从构建阶段到同源关系

**工程实践。** 用户态编排、C 原生库、PL 源码与 Overlay 各有构建入口。C 构建面向实际 ARM ABI 和目标系统库；PL 构建保存输入清单、原生执行日志、检查点和报告；Overlay 从已绑定的布线检查点导出。

**提炼过程。** 按产物划分应用、原生库、硬件构建和导出阶段，将每个阶段的输入、命令、报告与输出摘要连续记录。BIT、HWH 和 XSA 的对应关系通过实际内容校验建立，XSA 内部 BIT/HWH 与交付文件逐字节核对，DCP 内嵌 HWH 与导出 HWH 同步核对。

**形成的方法。** `xilinx-project-flow` 依据当前任务所需产物选择工具阶段，保留环境、器件、编译目标、脚本和输出身份；硬件交接同时记录文件摘要、构建来源与接口描述。

**落地文件。** [技能入口](../skill/xilinx-project-flow/SKILL.md)、[工程地图](../skill/xilinx-project-flow/references/project-map.md)、[交接证据门](../skill/xilinx-project-flow/references/evidence-gates.md)、[导出脚本](../build/export_overlay.py)。

**验证对应。** [Overlay 绑定文件](../build/overlay_candidate/binding.json)记录 `SOURCE_CHECKPOINT_REPORTS_OVERLAY_BOUND`，XSA 内 BIT/HWH 字节一致性为 `PASS`，DCP 内嵌 HWH 与导出 HWH 的字节一致性为 `PASS`。源码输入清单、布线检查点和实现报告通过相对路径及 SHA256 共同绑定。

### 7. PYNQ 加速器流程：从硬件接口经验到分阶段模板

**工程实践。** 摄像头交互系统的 PS/PL 协作涉及 IP 接口、地址窗口、时钟复位、软件驱动和硬件文件交接。技能包据此将 Overlay 构建所需的接口与验收步骤整理为可复用模板。

**提炼过程。** 将 HLS 与自定义 RTL 按 IP 来源分开组织，共同保留目标器件、工具版本、PS7 预设、请求时钟和寄存器契约。硬件步骤依次形成准备、功能仿真、综合、实现、报告门和导出；软件步骤形成驱动绑定、同步调用、异步调用和 Session 关闭。

**形成的方法。** `pynq-accelerator-flow` 提供 HLS 与 RTL 两套入口及配套资源，将 START 时的输入快照、完成状态、清除语义、中断、超时和所有权落实到寄存器及驱动契约。模板输入、阶段回执、报告与 BIT/HWH/XSA 通过摘要绑定，Notebook 和驱动共用会话。

**落地文件。** [技能入口](../skill/pynq-accelerator-flow/SKILL.md)、[RTL 路径](../skill/pynq-accelerator-flow/references/rtl-flow.md)、[HLS 路径](../skill/pynq-accelerator-flow/references/walkthrough.md)、[寄存器契约](../skill/pynq-accelerator-flow/references/register-contract.md)、[模板检查器](../skill/pynq-accelerator-flow/scripts/validate_template.py)。

**验证对应。** 技能验证记录保存了 RTL 标量模板的 121 项仿真断言、原生准备、顶层及 6 个必要 IP 的 OOC 综合结果；控制与 AXI-Stream/DMA 两类扩展案例完成了实际硬件综合、实现和导出。相关记录按模板与案例分别组织于[技能验证记录](../skill/references/validation-results.md)。

## 五、脚本化与离线复核

### 1. 将规则转成可执行入口

布局算术、HWH 文件解析、累计窗口计算和应用生命周期均形成独立主机入口。以下命令在工程包的 `skill/` 目录执行，各命令输入均来自技能包内文件。

```text
python -B pynq-dma-contract/scripts/check_layout.py pynq-dma-contract/examples/layout.json
python -B pynq-dma-contract/examples/lifecycle.py
python -B -m unittest discover -s pynq-dma-contract/scripts -p "test_*.py"
python -B pynq-development/scripts/inspect_hwh.py pynq-development/examples/synthetic.hwh --ip demo_dma
python -B stream-perf-analysis/scripts/analyze.py stream-perf-analysis/examples/performance.jsonl --contract stream-perf-analysis/references/project-perf-contract.json
```

| 入口 | 复核输出 | 对应提炼内容 |
| --- | --- | --- |
| 布局检查 | `PASS_STATIC_DESCRIPTION`，共 3 个缓冲描述 | 布局算术、地址范围、步幅与访问状态 |
| 生命周期示例 | `MOCK_LIFECYCLE_ONLY`，`owner=released` | 行复制、同步、提交与确认停止后的释放 |
| DMA 单元检查 | 18 项通过 | 7 项布局检查、11 项生命周期检查 |
| HWH 解析 | `OFFLINE_DECLARATIONS_ONLY`，示例地址窗口跨度 65536 B | 模块、VLNV、参数和地址声明提取 |
| 累计日志分析 | `valid_windows=1`，报告 24→25 | 同一连接中的连续报告差分 |

布局样例为合成的三缓冲描述：两个采集缓冲的步幅为 5760 字节，一个显示缓冲的步幅为 3840 字节，用于检查不同通道布局；工程实际运行采用前文列出的采集三槽与显示三槽。样例地址和设备实际分配地址分别使用各自的数据来源。

### 2. 将软件优化整理为可核对的实例

工程优化中的实现变化，为技能规则提供了具体实例：

| 工程实现 | 已归档结果 | 对技能方法的支撑 |
| --- | --- | --- |
| 4×4 BGR 采样与共享 HSV、颜色掩码 | 320×180 网格复用颜色结果 | 将数据复用关系纳入阶段与接口分析 |
